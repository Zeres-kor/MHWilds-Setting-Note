# 설계 통합 검수

상태: 문서 수준 1차 검토. 구현·브라우저 검증은 미실행.

## 대응 확인
- 보유 관리 요구 → INV-01~06 → 보유 입력·조회 흐름 → 보유 화면.
- 공통·무기 기준 업로드 → TAG-01~03 → 기준 갱신 흐름 → 기준 화면.
- 전체/보유 검색과 태그 표시 → SRCH-01~04 → 검색 흐름 → 검색 화면.
- 보존·재방문 → DATA-01 → 복원 흐름 → 백업 화면.

## 충돌 방지
- 태그 기준 호석은 보유 호석으로 저장하지 않는다.
- 전체 가능 호석 검색은 태그 기준 존재에 의존하지 않는다.
- 공통 태그를 무기별 태그로 덮어쓰지 않는다.
- 보유 여부는 종결 판정에 영향을 주지 않는다.
- 기존 TXT에 없는 레어도·메모·태그는 복구했다고 표시하지 않는다.
- 호석 태그는 세팅 전체의 강함 또는 실제 출현 확률을 의미하지 않는다.

## 구현 전에 해결할 항목
1. 원본 시뮬레이터 데이터·코드 접근 및 이용 조건 확인.
2. 엑셀 스킬 명칭 정규화, 중복 스킬·슬롯·레어도 규칙 확인.
3. 태그 엑셀 양식, 슬롯 비교, 우선순위 동률, 교체/병합 정의.
4. 보유 중복·수량과 삭제 시 저장 세팅 처리 정의.
5. 실행·저장 방식, 성능 목표와 검색 제한 표시 정의.

## 태그 상세 설계 진행
`TAG-RULES.md`와 빈 양식·비활성 예시 엑셀을 추가했다. 공통/무기 범위, 행 안 AND·같은 태그 행 OR, 종류별 슬롯 비교, 우선순위 충돌 검증, 업로드 교체/병합의 상세 제안을 담았다. 종결은 정확 일치, 준종결 이하 등급은 기준 이상, 같은 범위는 최우선 태그 하나 표시로 확정했다. 예시 파일은 이 정책에 맞춰 갱신했으며 모두 비활성이다. 앱의 업로드·판정 기능은 아직 구현하지 않았다.

## 검증 계획
- 태그 공통/무기 동시 판정, 수정·기준 변경·수동 태그 보존.
- 손상 파일과 오류 업로드가 기존 데이터를 변경하지 않음.
- 백업 후 복원한 관리 정보 일치.
- 작은 게임 데이터의 완전 탐색과 검색 엔진 결과 비교.
- 모든 결과의 호석 생성 규칙·장식주 배치·세트 발동 재검증.
- Windows 브라우저에서 입력→분류→필터→일괄 작업→백업·복원과 검색→저장 흐름 확인.
